# 城市公共自行车站点满桩调拨与维修平台

## 原始需求

开发城市公共自行车站点满桩调拨与维修平台，可使用 Vue 3、Go 和 PostgreSQL。用户借车时，平台核验账户、押金、车辆编号、站点状态和骑行限制；还车时，平台记录桩位、车辆锁止、费用、故障反馈和用户位置。运营端实时查看站点满桩、空桩、车辆故障、调拨车位置、早晚高峰需求和地铁口客流。若用户到站无法还车、站点无车、车辆刹车异常、锁具打不开、调拨车堵在路上或某站点长期潮汐失衡，平台要把用户、客服、调度员、维修员和站点管理员放到同一事件里处理。调拨策略需要考虑地铁早高峰、学校放学、商圈活动、维修车辆比例和调拨车容量。维修入库后，车辆故障类型、维修用时、配件消耗、重复故障和是否报废进入档案；站点调整时，运营可以看到用户流失、满桩投诉和调拨成本。平台还要把调拨车司机班次、站点电源、车辆清洗、用户骑行禁区、恶劣天气停运和地铁突发客流纳入运营判断。站点策略变化会影响用户通勤，所以调度动作需要能解释给客服和城市管理方。用户申诉时，平台要能从一次骑行回到借车桩位、还车状态、客服处理和调拨影响，运营需要判断费用、车辆和站点责任分别来自哪里。

## 本轮新增原始需求

增加高峰调拨路线。早高峰前，平台根据地铁口取车需求、住宅区还车积压和调拨车容量生成路线。调度员执行时，站点库存、车辆状态和预计到达会实时更新，偏离路线会影响后续站点补车。路线偏离如果是道路拥堵造成，调度员可以补充原因，避免司机被错误考核。偏离原因会进入调拨复盘，用于优化下一次路线。路线复盘会关联高峰天气。

### 新增需求 → 实现对照

| 需求点 | 实现 |
|---|---|
| 早高峰前按地铁口取车需求 + 住宅区还车积压 + 调拨车容量生成路线 | `POST /api/peak-routes/plan`：读 7 点（晚高峰 18 点）分时段需求预测，计算住宅装车点与地铁口卸车点，贪心装载并受车容量约束，生成有序多站路线与中文解释 |
| 调度员执行：站点库存 / 车辆状态 / 预计到达实时更新 | 详情页执行中 5 秒轮询；到达登记移动调拨车坐标并重算后续 ETA；装卸在事务内真实移动车辆（在桩⇄在途、占用/释放桩位），车上数量与站点库存实时变化 |
| 偏离路线影响后续站点补车 | 晚点到达自动判偏离，并给出对后续卸车站点的顺延影响；前车装车不足会级联导致后站少补，复盘统计「少补车辆」 |
| 道路拥堵可补充原因、免司机错误考核 | `POST .../stops/{seq}/deviation`：校验客观原因关键词（拥堵/管制/事故/恶劣天气等）才允许豁免；非客观原因勾豁免被拦截 |
| 偏离原因进入复盘、优化下一次路线 | `POST .../review` 汇总偏离/豁免/准点率/少补并归类原因；历史复盘的「道路拥堵」次数会让下一条路线自动预留行车缓冲 |
| 路线复盘关联高峰天气 | `peak_weather` 表按日期+早/晚高峰录入，复盘自动关联；橙/红预警路线再追加缓冲；复盘列表与偏离台账均展示天气 |

## 技术栈

- **前端**：Vue 3 + Vite + Vue Router + ECharts（构建产物由 Go 内嵌伺服）
- **后端**：Go 1.23（标准库 `net/http` 路由 + `lib/pq`），REST API，Token 会话
- **数据库**：PostgreSQL 16（首次启动自动建表 + 灌入演示数据）

## 一键启动（Docker）

```bash
cp .env.example .env        # 可选，默认值即可运行
docker compose up -d        # 构建并启动 app + db
docker compose ps           # 查看健康状态
```

- 应用端口通过环境变量 `CC_PUBLISH_PORT` 发布到宿主（compose 写法 `${CC_PUBLISH_PORT}:8080`）。
- 实际映射端口可用 `docker compose port app 8080` 查询，然后访问 `http://localhost:<端口>`。
- 数据库不发布宿主端口，仅在 compose 内部网络以服务名 `db` 访问。
- 停止：`docker compose down`（加 `-v` 可同时清空演示数据）。

**推荐演示路径**：
1. `rider2` 登录借车 → 押金不足被拦截；换 `rider3` → 骑行受限被拦截。
2. `rider1` 借车（选站点桩位上的车辆编号）→ 还车时选「万象城商圈站」（满桩）→ 触发 409 满桩 → 一键发起「无法还车」协同事件。
3. `disp1` 在事件里生成调拨任务 → 调拨中心派车 → 出车 → 完成（车辆真实搬移，看板同步变化）；点「堵车」自动生成拥堵事件。
4. `repair1` 在维修页接收故障 → 登记维修（选配件、填用时、可报废）→ 车辆档案可查履历与重复故障标记。
5. `cs1` 打开申诉 #1 → 查看借车桩位/还车状态/客服处理/调拨影响 → 填写三方责任与退费结案。
6. `ops1` 在运营判断发布「恶劣天气停运」→ `rider1` 借车被阻断；在站点页做扩容调整并查看流失/投诉/成本分析。
7. **【高峰调拨路线】`disp1` 打开「高峰调拨路线」→ 查看执行中的 `PR-0650`**：
   - 它已从滨江社区装车 10 辆、晚点到达地铁文化广场站（第 2 站已标记晚点、待补原因），页面顶部库存 / 车上数量 / 后续 ETA 实时刷新；
   - 点「补充原因」：先试非客观原因勾豁免（被拦截），再填「道路拥堵」并勾选豁免 → 免司机考核；
   - 依次「确认卸车补车」（地铁口在桩数 3→9）→ 到达第 3 站卸 4 辆（路线完成、车辆真实上桩）；
   - 「发起调拨复盘」→ 看准点率、拥堵豁免次数、少补车辆、关联的当日高峰天气与改进建议；
   - 回列表点「＋ 生成高峰路线」：新路线**住宅区装车点优先**（滨江社区→中心医院），并因昨日复盘有拥堵记录自动**预留 3 分钟缓冲**；
   - 「偏离台账」「调拨复盘」两个页签可按天气/豁免/考核结论回看历史路线。

## 验证方式

本项目以「宿主 `docker compose up` 健康 + 关键业务流走通」为验证标准：

```bash
docker compose up -d --build
docker compose ps                                  # app/db 均 healthy
PORT=$(docker compose port app 8080 | cut -d: -f2)
curl -s "http://host.docker.internal:$PORT/api/health"            # {"status":"ok"}
# 登录 → 借车 → 还车 → 事件 → 调拨 → 维修 → 申诉，均可通过界面或 API 走通
docker compose down
```

### 高峰路线 API 一览

| 方法与路径 | 角色 | 说明 |
|---|---|---|
| `POST /api/peak-routes/plan` | 调度员/运营 | 依据地铁取车需求、住宅还车积压、车容量生成有序多站路线（含复盘学习缓冲） |
| `POST /api/peak-routes/{id}/assign`、`/start` | 调度员/运营 | 派车（校验容量）、出车开始执行 |
| `POST /api/peak-routes/{id}/stops/{seq}/arrive` | 调度员/运营 | 登记到达：移动车辆坐标、实时重算后续 ETA，晚点自动判偏离并提示影响 |
| `POST /api/peak-routes/{id}/stops/{seq}/execute` | 调度员/运营 | 装车/卸车：真实移动车辆与桩位，更新车上数量与站点库存，末站自动完成 |
| `POST /api/peak-routes/{id}/stops/{seq}/deviation` | 调度员/运营 | 补充偏离原因；道路拥堵等客观原因可豁免司机考核 |
| `POST /api/peak-routes/{id}/review` | 调度员/运营 | 复盘：准点率/偏离/豁免/少补、关联当日高峰天气、产出优化建议 |
| `GET /api/peak-routes`、`/{id}`、`/deviations`、`/reviews` | 任意员工 | 路线、执行详情、偏离台账、复盘列表 |
| `GET/POST /api/peak-weather` | 员工 / 调度员·运营 | 高峰天气查询与录入（复盘自动关联） |
