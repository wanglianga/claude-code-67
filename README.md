# 城市公共自行车站点满桩调拨与维修平台

## 原始需求

开发城市公共自行车站点满桩调拨与维修平台，可使用 Vue 3、Go 和 PostgreSQL。用户借车时，平台核验账户、押金、车辆编号、站点状态和骑行限制；还车时，平台记录桩位、车辆锁止、费用、故障反馈和用户位置。运营端实时查看站点满桩、空桩、车辆故障、调拨车位置、早晚高峰需求和地铁口客流。若用户到站无法还车、站点无车、车辆刹车异常、锁具打不开、调拨车堵在路上或某站点长期潮汐失衡，平台要把用户、客服、调度员、维修员和站点管理员放到同一事件里处理。调拨策略需要考虑地铁早高峰、学校放学、商圈活动、维修车辆比例和调拨车容量。维修入库后，车辆故障类型、维修用时、配件消耗、重复故障和是否报废进入档案；站点调整时，运营可以看到用户流失、满桩投诉和调拨成本。平台还要把调拨车司机班次、站点电源、车辆清洗、用户骑行禁区、恶劣天气停运和地铁突发客流纳入运营判断。站点策略变化会影响用户通勤，所以调度动作需要能解释给客服和城市管理方。用户申诉时，平台要能从一次骑行回到借车桩位、还车状态、客服处理和调拨影响，运营需要判断费用、车辆和站点责任分别来自哪里。

## 技术栈

- **前端**：Vue 3 + Vite + Vue Router + ECharts（构建产物由 Go 内嵌伺服）
- **后端**：Go 1.23（标准库 `net/http` 路由 + `lib/pq`），REST API，Token 会话
- **数据库**：PostgreSQL 16（首次启动自动建表 + 灌入演示数据）

## 一键启动（Docker）

```bash
cp .env.example .env        # 可选，默认值即可运行
docker compose up -d        # 构建并启动 app + db
docker compose ps           # 查看健康状态
```

- 应用端口通过环境变量 `CC_PUBLISH_PORT` 发布到宿主（compose 写法 `${CC_PUBLISH_PORT}:8080`）。
- 实际映射端口可用 `docker compose port app 8080` 查询，然后访问 `http://localhost:<端口>`。
- 数据库不发布宿主端口，仅在 compose 内部网络以服务名 `db` 访问。
- 停止：`docker compose down`（加 `-v` 可同时清空演示数据）。

## 功能地图（需求 → 实现）

| 需求 | 实现位置 |
|---|---|
| 借车核验（账户/押金/车辆编号/站点状态/骑行限制） | `POST /api/rides/borrow`，前端「借车/还车」页逐项拦截并提示 |
| 还车记录（桩位/锁止/费用/故障反馈/用户位置） | `POST /api/rides/{id}/return`，事务内分配桩位、锁车、计费、建故障单 |
| 运营实时总览（满桩/空桩/故障/调拨车/高峰/地铁客流） | 「实时运营看板」5 秒轮询，SVG 地图 + ECharts |
| 六类异常多方协同事件 | 「协同事件」：自动拉入用户/客服/调度/维修/站管，时间线 + 处置动作（生成调拨/派维修/免费用）|
| 调拨策略（地铁早高峰/放学/商圈/维修比例/车容量） | 调拨中心「生成调拨计划」，因子可勾选，产出带中文解释的任务 |
| 维修档案（故障类型/用时/配件/重复故障/报废） | 「维修与车辆档案」：登记维修扣减配件库存，30 天同车同类自动标重复，可报废 |
| 站点调整分析（用户流失/满桩投诉/调拨成本） | 「站点与调整分析」弹窗 + 调整记录（容量变更同步桩位） |
| 运营判断（班次/电源/清洗/禁区/停运/突发客流） | 「运营判断」页，天气停运会真实阻断借车接口 |
| 调度动作可解释 | 每个调拨任务携带 `explanation` 与因子标签，客服/城管角色可查看 |
| 申诉溯源与三方定责 | 「申诉处理」详情：骑行链路 + 客服协同记录 + 调拨影响 + 费用/车辆/站点责任判定与退费 |

## 演示数据

首次启动自动灌入：8 个站点（地铁口/学校/商圈/社区）、61 辆车（含故障/在修/在途/清洗/报废）、3 辆调拨车与司机班次、30+ 历史行程、4 个协同事件（含已解决样例）、2 条申诉、满桩/空桩投诉、地铁口 24 小时客流（含 18 点突发客流预警）、分站点分时段需求预测、配件库存、清洗计划、禁区与历史天气预警。

**推荐演示路径**：
1. `rider2` 登录借车 → 押金不足被拦截；换 `rider3` → 骑行受限被拦截。
2. `rider1` 借车（选站点桩位上的车辆编号）→ 还车时选「万象城商圈站」（满桩）→ 触发 409 满桩 → 一键发起「无法还车」协同事件。
3. `disp1` 在事件里生成调拨任务 → 调拨中心派车 → 出车 → 完成（车辆真实搬移，看板同步变化）；点「堵车」自动生成拥堵事件。
4. `repair1` 在维修页接收故障 → 登记维修（选配件、填用时、可报废）→ 车辆档案可查履历与重复故障标记。
5. `cs1` 打开申诉 #1 → 查看借车桩位/还车状态/客服处理/调拨影响 → 填写三方责任与退费结案。
6. `ops1` 在运营判断发布「恶劣天气停运」→ `rider1` 借车被阻断；在站点页做扩容调整并查看流失/投诉/成本分析。

## 验证方式

本项目以「宿主 `docker compose up` 健康 + 关键业务流走通」为验证标准：

```bash
docker compose up -d --build
docker compose ps                                  # app/db 均 healthy
PORT=$(docker compose port app 8080 | cut -d: -f2)
curl -s "http://host.docker.internal:$PORT/api/health"            # {"status":"ok"}
# 登录 → 借车 → 还车 → 事件 → 调拨 → 维修 → 申诉，均可通过界面或 API 走通
docker compose down
```
